## Upgrade behavior

`1.18.3 -> 1.18.4` validates required installed capabilities and does not change stored
observations, dimensions, configuration signatures or schemas. It schedules no replay
and requests no nuclear resync. Existing history is preserved. Missing historical
weights/metadata can be repaired separately through reviewed, targeted scheduling.

Only 1.18.3 is a direct predecessor. Older tenants still traverse their normal upgrade
path, including the potentially long GSC migration in 1.18.3. Preserve the existing
backup, durable operation and maintenance-window practices; no routine is bypassed.

## Facade registration

Deploy the matching Facade source and execute:

```sh
php artisan db:seed --class=ApisHubReleaseV1184Seeder --force
```

The seeder idempotently registers v1.18.4 as active/default, preserves v1.18.3's channel
and configuration definitions, leaves earlier upgrade-impact metadata intact and
dispatches no tenant upgrade or resync. Release 1.18.4 itself has no large-history
migration impact. Registration requires the release tag to be available to the
deployment server before users start upgrades.

The local release tag is not a production deployment. Publish the committed tag
through the normal release process, run controlled source/PostgreSQL acceptance,
then register and pilot the upgrade before broader tenant rollout.
